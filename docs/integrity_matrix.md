# Integrity matrix

Every rule that rejects a bad write in either database, paired with its counterpart in the other and with the test that proves it. Task 3.5a (BUILD_PLAN section 11 and the section 6 row "Integrity and security: each bad write rejected by both").

## How it is built

- The rules are read from the live catalogues, not from the SQL and JSON files:
  - PostgreSQL: every constraint of type `c`, `f`, `n`, `p` and `u` on the nine application tables, every unique index that has no constraint (`buyer_email_lower_key`), every trigger, and every `VARCHAR(n)` and `NUMERIC(p,s)` column (key `pg:<table>.<column>:type`). Key: `pg:<table>.<name>`.
  - MongoDB: every `required` entry, `bsonType`, `minimum`, `maximum`, `maxLength`, `pattern`, `enum`, `minItems`, `maxItems` and `additionalProperties: false` in the `$jsonSchema` of each collection, found through `listCollections`, at every level (`properties`, `items`, `anyOf`, `not`). Key: `mongo:<collection>:<json path>:<keyword>`, where the path starts at `$jsonSchema`, an array's elements are `items` and a required field is `required.<field>`. The comparisons inside `$expr` are keyed by their full JSON path, for example `mongo:building_profiles:$expr.$cond.2.$and.1.$lte`.
- `tests/negative/test_matrix.py` fails if a live rule has no row, if a row names a rule that no longer exists, if a listed test does not exist (node ids come from a separate `pytest --collect-only` over `tests/`), or if a rule has no case of its own. Test ids are the rule keys; a PostgreSQL rule that MongoDB splits into clauses has one case per clause, `<key>#<clause>`.
- `tests/negative/test_pg_rules.py` and `tests/negative/test_mongo_rules.py` hold the cases. Each shows that a baseline row or document is accepted, changes exactly one value, and asserts the exact error: the SQLSTATE and constraint name (or table and column for NOT NULL, which reports no constraint) in PostgreSQL; code 121 and the failing property and keyword in MongoDB.

## Reading a row

- A cell with no key starts with `none:` (the other database has nothing to enforce) or `app layer:` (the application enforces it, with the reason).
- Tests listed without an id of the form `test_pg_rule[...]` or `test_mongo_rule[...]` are earlier tests that already cover the rule (PR #10, 3.2 and 3.3), referenced rather than repeated. For a parametrised test one id is shown.
- MongoDB reports an `$expr` failure only as `operatorName: "$expr"` for the whole expression, so those cases assert that and that no schema rule failed; the baseline method shows which value caused it.
- MongoDB reports a `not` failure only as `child expression matched`, so the case for `anyOf.1.not:required.supply` asserts `not` at `anyOf.1`.
- A required `_id` cannot be tested by omitting it, because the driver supplies an ObjectId; the case for `required._id` asserts that the ObjectId then fails the `_id` type rule.
- The root `bsonType: object` of a validator cannot fail, so its case asserts that the live rule is present.
- Unique indexes in MongoDB (`block_street_unique`, `email_unique` and the `_id` index) are not validator rules, so they are not enumerated; `test_mongo_unique_index` covers them and the rows name them.
- Writes use the identity that could otherwise write the table: `app_rw` for `buyer` and `saved_building`, `app_admin` for `resale_transaction`, the schema owner for the rest; in MongoDB `etl` for `building_profiles` and `hawker_centres`, `app_admin` for `resale_transactions` and `app` for `buyers` and `counters` (inside a transaction that is aborted).
